# תוכנית QA למוצרי תוכנה ומערכות AI

מאגר זה מכיל **תוכנית בדיקות (QA Test Plan)** שמטרתה לסייע בבדיקת מוצר תוכנה, סוכן AI או אוטומציה לפני שימוש או שחרור גרסה.

**[למעבר למסמך הבדיקות המלא — QA_TEST_PLAN.md](QA_TEST_PLAN.md)**

## מהו QA ולמה הוא חשוב?

**QA — Quality Assurance (הבטחת איכות)** הוא תהליך שמטרתו לוודא שהמוצר עומד בדרישות, עובד באופן אמין, שומר על מידע ומטפל נכון בתקלות. במסמך הבדיקות מופיע **Checklist**: רשימת פעולות לבדיקה, ולא אישור שהבדיקות כבר בוצעו.

## 1. פירמידת הבדיקות — Test Pyramid

הפירמידה מחלקת את הבדיקות לארבע רמות, מהחלקים הקטנים של המערכת ועד להתאמה לצורכי המשתמש.

| רמה | המשמעות | דוגמה במערכת AI / אוטומציה |
| --- | --- | --- |
| **Unit Testing — בדיקות יחידה** | בדיקה של פונקציה או רכיב בנפרד: חישובים, קלט, שגיאות ומבנה פלט. | האם חישוב עלות בקשה מחזיר סכום מדויק? |
| **Integration Testing — בדיקות אינטגרציה** | בדיקה של התקשורת והנתונים שעוברים בין רכיבים ושירותים. | האם Webhook מעביר את כל השדות מ־Make למערכת היעד? |
| **System Testing — בדיקות מערכת** | בדיקת התהליך השלם מתחילתו ועד סופו, כולל מצבי כשל. | האם בקשה מתקבלת, נבדקת ונשמרת כראוי? |
| **Acceptance Testing / UAT — בדיקות קבלה** | בדיקה שהמוצר עומד בדרישות העסקיות ושהשימוש בו מתאים למשתמש. | האם בקשה מעל 3,000 ש״ח מסומנת לאישור מנהל, ולא מתבצעת הזמנה אוטומטית? |

**העיקרון:** לרוב מבצעים יותר בדיקות יחידה ממוקדות, ופחות בדיקות מערכת רחבות ומורכבות. זהו כלל מנחה, לא מכסה מחייבת.

## 2. בדיקות משלימות — מה בודקים ולמה?

הבדיקות הבאות יכולות להשתלב בכל אחת מרמות הפירמידה.

| סוג בדיקה | המשמעות ומה חשוב לבדוק |
| --- | --- |
| **Functional Testing — פונקציונליות** | האם הפעולות, שדות החובה והכללים העסקיים מתנהגים כפי שהוגדר? האם הודעות המשתמש מובנות? |
| **Edge Cases — מקרי קצה** | מה קורה כשהקלט ריק, שגוי, כפול, סותר או בדיוק בערך הגבול? מה קורה כששירות חיצוני נופל? |
| **Non-Functional Testing — לא פונקציונליות** | האם המערכת מהירה, יציבה, נגישה ושימושית? האם היא עומדת בעומס ובזמני התגובה שהוגדרו? |
| **Data Integrity — שלמות נתונים** | האם שדות ממופים נכון, סוגי הנתונים תקינים, ואין איבוד מידע או כפילויות? האם מידע רגיש נשמר מחוץ ללוגים מיותרים? |
| **Security & Risk — אבטחה וסיכונים** | האם הרשאות נאכפות? האם סיסמאות ומפתחות מוגנים? האם קלט זדוני ופעולות רגישות מטופלים בבטחה? |

## 3. בדיקות ייעודיות ל־AI — AI Quality Assurance

מערכת AI דורשת בדיקות נוספות, כי תשובות המודל עשויות להשתנות גם עבור בקשות דומות.

| נושא | משמעות הבדיקה |
| --- | --- |
| **דיוק ורלוונטיות** | האם התשובה עונה לבקשה ומבוססת על המידע המתאים? |
| **Hallucinations — הזיות** | האם המודל נמנע מהצגת עובדות שלא אומתו כאילו הן ודאיות? |
| **Prompt Injection** | האם הוראות זדוניות בקלט או בתוכן חיצוני אינן עוקפות את כללי הסוכן? |
| **Tool Calling — הפעלת כלים** | האם הסוכן משתמש בכלי הנכון, עם נתונים והרשאות תקינים, ומבקש אישור לפני פעולה רגישה? |
| **JSON Schema / מבנה פלט** | האם התשובה מכילה את השדות, הסוגים והפורמט שהמערכת דורשת? |
| **פרטיות** | האם מידע אישי או רגיש אינו נחשף למשתמש או לשירות שאינו מורשה? |
| **Regression Testing — בדיקות רגרסיה** | האם שינוי בפרומפט, במודל או בתהליך לא פגע בהתנהגות שכבר עבדה? |
| **איכות, זמן ועלות** | האם שיעור ההצלחה, זמן התגובה ועלות ההרצה עומדים ביעדים שהוגדרו? |

**דוגמה:** בסוכן בקשות ציוד, בקשה בסכום של 3,001 ש״ח אמורה לקבל סטטוס של אישור מנהל; יש לבדוק גם את הגבול של 3,000 ש״ח בדיוק, בהתאם לדרישה העסקית. הסוכן לא אמור לבצע הזמנה אוטומטית אם הדבר נאסר בדרישות.

## 4. איך משתמשים במסמך הבדיקות?

1. פותחים את **[QA_TEST_PLAN.md](QA_TEST_PLAN.md)** וממלאים שם פרויקט, גרסה, סביבת בדיקה, בודק ותאריך.
2. מגדירים לכל בדיקה תרחיש, קלט ותוצאה צפויה שמתאימים למערכת הנבדקת.
3. מריצים את הבדיקה בפועל ומתעדים את התוצאה ואת הראיות (למשל צילום מסך, לוג או קישור לתקלה).
4. מסמנים `- [x]` רק לאחר ביצוע הבדיקה; תיבת סימון אינה מעידה לבדה על הצלחה.
5. בודקים את **תנאי אישור הגרסה** לפני שחרור המערכת.

### איך מתעדים תוצאה?

| שדה | תפקיד |
| --- | --- |
| **Test ID** | מזהה ייחודי כגון `QA-001`. |
| **תרחיש וקלט** | מה נבדק ואילו נתונים נשלחו. |
| **תוצאה צפויה** | מה המערכת הייתה אמורה לעשות. |
| **תוצאה בפועל** | מה התרחש בהרצה. |
| **ראיות** | תיעוד שניתן לבדוק בדיעבד. |
| **סטטוס** | מצב הבדיקה, לפי הערכים שלהלן. |

| סטטוס | משמעות |
| --- | --- |
| `PASS` | הבדיקה עברה — התוצאה תואמת לצפוי. |
| `FAIL` | הבדיקה נכשלה — התוצאה אינה תואמת לצפוי. |
| `BLOCKED` | לא ניתן להשלים את הבדיקה בגלל חסימה. |
| `NOT RUN` | הבדיקה עדיין לא בוצעה. |

## 5. מתי מאשרים גרסה? — Release Criteria

אישור גרסה נשקל רק לאחר שהבדיקות הקריטיות ובדיקות הקבלה הושלמו בהצלחה, נבדקו אבטחה, פרטיות, נתונים וביצועים, ותועדו תקלות ומגבלות ידועות. יש לקבל החלטה מתועדת על תקלות חמורות פתוחות ולהכין דרך חזרה לגרסה קודמת במקרה הצורך.

**חשוב:** מסמך זה הוא תבנית לתכנון ולתיעוד QA, ולא הוכחה לכך שמוצר מסוים נבדק או אושר. את רשימת הבדיקות יש להתאים לדרישות, לסיכונים ולסביבת העבודה של כל פרויקט.
